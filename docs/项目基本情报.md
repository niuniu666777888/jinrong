# 项目基本情报

> 一句话：为支付运营团队做一套「对账 + 差错追踪」系统，把每天对不上的账变成**可解释、可追溯、有人负责**的差异单。
> 系统只做匹配、分类与线索，**不改资金、不生成凭证、不替人下结论**。

- 业务体量：日均 **80 万笔**交易，2 家渠道起步
- 现状痛点：未解释差异每天 **180 笔**，从发现到定位平均 **6 小时**
- 目标：未解释差异降到 **40 笔**，定位时长压到 **1 小时**，自动匹配率 **≥ 99.9%**
- 一期预算：**26 万元**（单渠道、只读回放、差异闭环）

---

## 一、问题：对账为什么对不上

对账的本质是拿「渠道账单」和「内部交易流水」逐笔比。比不上的原因集中在三类，且互相叠加：

| 根因 | 表现 | 后果 |
|---|---|---|
| **跨日退款** | 退款当日发起、渠道次日入账；内部按退款事件时间记账，渠道按入账日记账 | 两侧都能找到单，但因日期不同被判成差异 |
| **手续费合并入账** | 渠道按批次扣费、合并入账，单笔金额与内部流水不一致 | 逐笔比必然不平，只能整批重算 |
| **主键与口径不一致** | 交易号、商户订单号、渠道流水号关系不完整；时区不统一 | 匹配不上，也无法判断是真差异还是口径问题 |

现状链路由人工串起来：日切拉单 → 下载账单导入 Excel → 逐笔比对 → 翻流水找渠道确认 → 台账建单 → 口头复核 → 调整归档。每一步都靠人盯，差异一多就漏，复核也留不下痕迹。

## 二、范围：做什么、不做什么

| 做（一期至三期） | 不做（明确排除） |
|---|---|
| 渠道适配器（一期先做 1 个渠道） | 资金划拨、代付、退款执行（走原有支付系统） |
| 账单解析、批次管理、重跑与幂等 | 会计凭证生成（交财务总账） |
| 明细逐笔匹配 + 汇总/笔数/状态核对 | 商户结算规则、费率配置（沿用现有商务系统） |
| 差异池、七类差错分类、证据链 | 自动调账、自动定性为最终结论 |
| 工单、交接、驳回、超时升级 | 替代支付网关的交易处理职能 |
| 双人复核、结算文件生成、平账归档 | 对外承诺赔付、直接答复商户 |

**边界一句话**：系统位于「支付渠道」与「财务总账」之间，向上接账单与流水，向下输出对账结果、差异单与结算文件；不处理交易请求，不持有资金。

## 三、十条架构决策（摘要）

| # | 议题 | 决策 |
|---|---|---|
| 1 | 系统边界 | 全域自建对账链路，不做只读辅助层 |
| 2 | 主键与时区 | 商户订单号为主键、渠道流水号为资金键，统一 UTC+8 |
| 3 | 规模与时效 | 日 80 万笔，T+1 全量 + 小时级增量，批量窗口 ≤ 2 小时 |
| 4 | 差错定性 | 七类差错，系统自动初判 + 人工改判，改判须留原因 |
| 5 | 工单模型 | 自建轻量状态机 + 交接五要素，不引入 BPMN |
| 6 | AI 边界 | L1 线索排序、L2 原因推荐、L3 动作建议需签核；模型不写业务表 |
| 7 | 角色权限 | 六岗 RBAC + 数据域 + 职责分离互斥 |
| 8 | 集成方式 | 只读接入，差异落本地库；断连用快照降级 |
| 9 | 部署合规 | 私有化内网 + 本地模型，账单含个人金融信息，禁止出境 |
| 10 | 验收口径 | 自动匹配率 ≥ 99.9%，差异可解释率 100% |

## 四、角色与职责分离

六个业务岗位（运营经理、渠道运营员、对账会计、数据工程师、资金风险经理、商户服务主管）+ 一个系统管理员。**不用「员工 / 管理员」两分法**——审计第一个问题就是「谁复核的」，两分法里没人能回答。

四条由系统强制、不依赖流程约定的硬约束：

1. 同一差异单的**发起人与复核人不能是同一人**，提交复核时直接拦截并记录拦截日志；
2. 资金调整必须两人四眼，A 提交、B 复核；任一方缺位由运营经理指定代理人并留痕；
3. 规则版本变更需运营经理审批 + 风险经理知会，变更前后快照存档，历史单据按当时版本复算；
4. 数据导出需二次确认，记录导出人、范围、用途；单次超 1 万条需风险经理审批。

## 五、口径：三个编号、四条时间轴

**三个编号不能混用**：商户订单号是业务主键（对账匹配的锚点）；渠道流水号是资金键（与渠道账单逐笔核对的凭证）；内部交易号是系统键（溯源）。

**四条时间轴必须分开存**（合并成一个日期字段，就是跨日退款对不上的根源）：

| 字段 | 含义 | 来源 |
|---|---|---|
| `pay_time` | 支付发生时间（渠道事件时间） | 渠道账单 |
| `booking_date` | 内部记账日期 | 内部流水 |
| `settlement_date` | 渠道结算日期 | 结算账单 |
| `ingest_time` | 数据入库时间 | 系统生成 |

日切统一按 UTC+8 的 00:00，但**结算日以渠道账单标注为准**。渠道字段到内部字段的映射放进「口径字典」，带转换规则、生效日期、版本号与维护人；所有匹配、统计、对外答复都从字典取值，不允许在代码里写死。

## 六、七类差错与处理

系统输出「初判 + 置信度 + 证据」，**定性为最终结论必须由对账会计确认**；改判留原因，以版本化方式追加，不覆盖原判断。

| 类型 | 判定特征 | 系统动作 | 人工动作 |
|---|---|---|---|
| 长款 | 渠道有记录、平台无有效订单（多收） | 自动标长款，附渠道流水 | 核实后补单或退款 |
| 短款 | 平台显示成功、渠道未收到（少收） | 自动标短款，冻结结算 | 调单核查、补偿扣款 |
| 金额不符 | 主键匹配但金额差 > 0.01 元 | 标金额不符，列出差额 | 核对费率/找零/优惠分摊 |
| 状态不符 | 金额一致、订单状态未更正 | 标状态不符，触发状态补偿 | 补状态或人工更正 |
| 重复单 | 同订单号多笔成功 | 标红，暂停该单结算 | 确认保留哪笔、冲正其余 |
| 跨日退款 | 退款时间与支付日跨日 | 按口径字典归属，标跨日 | 核对归属日与报表一致 |
| 手续费/汇率差异 | 净额差 = 手续费或汇率折算差 | 按规则重算并对比 | 确认费率版本或汇率取值 |

匹配按置信度分层：主键精确匹配 1.00 → 主键 + 金额容差 0.98 → 时间窗/一对多归并 → 仍不匹配进差异池。低于阈值不硬匹配，避免「猜着匹配」把真差异藏起来。

## 七、验收指标（首期）

| 指标 | 口径 | 目标 |
|---|---|---|
| 自动匹配率 | 分母＝当日应匹配笔数（剔除口径歧义记录） | ≥ 99.9% |
| 差异可解释率 | 每条差异至少 1 条证据 + 1 个差错分类 | 100% |
| 未解释差异 | 每日未归因差异笔数 | 180 → 40 笔 |
| 发现到定位时长 | 账单入库至差异定性的 P90 时长 | 6 小时 → 1 小时 |
| 双人复核执行率 | 资金调整单中复核人 ≠ 发起人的比例 | 100% |

## 八、三条不可退让的硬约束

| 约束 | 含义 | 落地方式 |
|---|---|---|
| **只读不改资金** | 系统不发起退款、调账、划拨，只输出差异与线索 | 接口全只读；资金动作跳转原有系统 |
| **结论必须人签** | 规则与 AI 只给候选，定性与复核由人签字 | 复核意见必填；发起人 ≠ 复核人 |
| **审计可重建** | 每条差异可按业务编号回溯到原文、规则版本与处理人 | 证据表 + 审计日志 + 模型调用记录 |

## 九、数据与技术

- **数据**：仓库内全部为**合成数据**，无真实客户、账号或金额；受访人姓名与单位均为虚构。
- **技术选型**：关系库 PostgreSQL（分区表 + 物化视图）；对象存储保存原始账单与证据；调度 XXL-Job / Quartz；差异量大时用消息队列解耦工单。
- **部署**：私有化内网 + 本地模型。账单含个人金融信息，禁止出境与出网。
- **仓库内对应实现**：`src/`（最小可运行版：问答 + 差错闭环）、`支付对账与差错追踪系统_交付/`（完整交付版）。
