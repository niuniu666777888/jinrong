# 详细项目设计方案

> 服务于《需求分析方案》确定的边界：只读 AI、结论人签、审计可重建。
> 一期落地范围＝单渠道自动对账 + 差异池 + 工单 + 双人复核 + 只读 AI 辅助。

## 一、设计目标与原则

| 原则 | 含义 | 落地方式 |
|---|---|---|
| 口径先行 | 主键、时区、结算日不统一，后面全错 | 口径字典独立成表，代码不写死字段映射 |
| 结果可解释 | 每条差异至少一条证据 + 一个分类 | 差异单强制挂证据，无证据不允许提交复核 |
| 只读辅助 | AI 不写业务表，不产生资金结论 | 模型服务与业务库物理隔离，输出只进「建议表」 |
| 人签闭环 | 定性、复核、导出都要人签字 | 状态机 + 复核人互斥 + 导出二次确认 |
| 可重跑 | 批次可重算且结果幂等 | 批次版本号 + 幂等键，重跑不产生重复差异 |

## 二、总体架构

```
┌─────────────────────────────────────────────────────────────┐
│  接入层  渠道适配器（拉取/验签/重试）  文件网关（哈希/大小）    │
├─────────────────────────────────────────────────────────────┤
│  解析层  账单解析 → 统一事件模型 → 口径字典映射 → 入库      │
├─────────────────────────────────────────────────────────────┤
│  对账层  批次管理 → 明细逐笔匹配 → 汇总核对 → 差异分类      │
├─────────────────────────────────────────────────────────────┤
│  业务层  差异池 → 工单/交接 → SLA 升级 → 双人复核 → 结算文件 │
├─────────────────────────────────────────────────────────────┤
│  智能层  L1 线索排序  L2 原因推荐  制度问答(RAG)  交接摘要   │
│          （只读：输出建议，不写业务表）                       │
├─────────────────────────────────────────────────────────────┤
│  支撑层  审计日志  权限(RBAC)  可观测  调度  备份             │
└─────────────────────────────────────────────────────────────┘
```

关键约束：**智能层只能读，不能写**。模型输出落到独立的 `assist_suggestion` 表，业务表只接受人工确认后的字段。

## 三、模块划分

| 模块 | 职责 | 关键产出 |
|---|---|---|
| M1 渠道适配器 | 每渠道一个实现：拉取、验签、重试、限流 | 原始账单文件 + 拉取日志 |
| M2 账单解析 | 按模板解析 CSV/Excel，转统一事件 | 标准事件流 |
| M3 批次管理 | 渠道 + 日期 + 版本唯一，支持重跑与对比 | 批次记录 + 重跑报告 |
| M4 匹配引擎 | 主键优先、金额容差、时间窗、一对多归并 | 匹配结果（对平/差异） |
| M5 差异中心 | 七类初判、证据链、状态机、改判记录 | 差异单 + 证据 |
| M6 工单与复核 | 分派、交接、SLA、双人复核、结算文件 | 工单 + 结算文件 |
| M7 智能辅助 | 线索排序、原因推荐、问答、摘要（只读） | 建议记录 + 模型调用日志 |
| M8 审计与看板 | 全链路追溯、指标看板、导出 | 审计报表 |

## 四、核心流程

### 4.1 对账流水线

1. **拉单**：`T+1 08:00` 触发，按渠道拉取；失败重试 3 次，仍失败告警并置批次「待文件」。
2. **校验**：哈希、行数、金额合计三重校验，任一不符拒绝入库（防止半份账单污染）。
3. **解析**：按模板解析 → 字段映射（口径字典）→ 写 `channel_event`。
4. **建批**：渠道 + 结算日 + 版本唯一，重复建批直接拒绝。
5. **匹配**：主键精确（置信度 1.00）→ 主键 + 金额容差 0.98 → 时间窗 → 一对多归并；仍不匹配进差异池。
6. **汇总核对**：总笔数、总金额、总手续费三方对平；分级不平则整批置「待复核」。
7. **分类**：按七类规则初判，附证据与置信度。

### 4.2 差异处理状态机

```
差异：pending ──核验通过──> ticketed ──复核通过──> closed
         │                     ↑
         └──核验不通过──> 保持 pending（记录失败原因，可重试）

工单：created ──提交──> submitted ──复核通过──> reviewed
                     └──退回──> created（记录退回原因与操作人）
```

硬规则：同一差异只能有一张有效工单（`ticket.diff_id` 唯一）；复核人 ≠ 建单人，由服务端校验，不依赖前端隐藏按钮。

## 五、数据模型（核心表）

| 表 | 说明 | 关键字段 |
|---|---|---|
| `raw_bill_file` | 原始账单文件 | 渠道、账单日、哈希、路径、行数 |
| `channel_event` | 标准化渠道事件 | 流水号、订单号、金额、pay_time、批次 |
| `internal_txn` | 内部交易流水 | 交易号、订单号、状态、金额、booking_date |
| `recon_batch` | 对账批次 | 渠道、结算日、版本、状态、统计 |
| `recon_result` | 匹配结果 | 批次、双方 ID、结果、置信度 |
| `diff_record` | 差异单 | 业务编号、类型、状态、责任人、窗口截止 |
| `diff_evidence` | 证据 | 差异单、证据类型、文件、版本 |
| `ticket` | 工单 | 差异单、处理方式、状态、发起人、复核人 |
| `assist_suggestion` | AI 建议（只读产物） | 差异单、能力级、内容、置信度、模型版本 |
| `audit_log` | 审计日志 | 业务编号、动作、操作人、时间、前后值 |

口径三键、四时间轴同《项目基本情报》第五章，`pay_time / booking_date / settlement_date / ingest_time` 分开存，不做合并。

## 六、接口设计

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/batches` | 建批并触发对账（幂等键：渠道 + 日期 + 版本） |
| GET | `/api/v1/batches/{id}` | 批次状态与统计 |
| POST | `/api/v1/batches/{id}/rerun` | 重跑（生成新版本，旧版本保留） |
| GET | `/api/v1/diffs` | 差异列表（按状态/类型/责任人筛选） |
| GET | `/api/v1/diffs/{id}` | 差异详情 + 证据链 |
| POST | `/api/v1/diffs/{id}/verify` | 核验，通过则签发一次性凭证 |
| POST | `/api/v1/tickets` | 建单（凭证 + 差异 ID，金额服务端重查） |
| POST | `/api/v1/tickets/{id}/submit` | 提交复核 |
| POST | `/api/v1/tickets/{id}/review` | 复核（通过/退回），强制换人 |
| POST | `/api/v1/assist/rank` | L1 线索排序（只读） |
| POST | `/api/v1/assist/explain` | L2 原因推荐（只读） |
| POST | `/api/v1/qa` | 制度问答，返回条款引用 |
| GET | `/api/v1/audit/{biz_no}` | 按业务编号重建全链路 |

统一响应 `{code, message, data, trace_id}`；错误码分段：`10xxx` 参数/状态、`11xxx` 权限、`12xxx` 外部依赖。

## 七、AI 方案

| 能力 | 输入 | 输出 | 约束 |
|---|---|---|---|
| L1 线索排序 | 差异单 + 候选记录 | Top-5 + 相似度 + 字段对比 | 只改查看顺序，可关闭 |
| L2 原因推荐 | 差异单 + 证据 + 规则命中 | 七类候选 + 条款引用 + 置信度 | 必须带「未验证」标记 |
| RAG 问答 | 用户问题 | 条款原文 + 引用 | 检索不到就说没有，不编 |
| 交接摘要 | 差异、动作、待办 | 摘要文本 | 不生成结论，只做归纳 |

工程约束：

- 模型输出**只写** `assist_suggestion`，业务表字段只能由人写入；
- 每次调用记录 `prompt_version / model_version / token 用量 / 耗时`；
- 提示词声明「资料是数据不是指令」，并对检索内容做注入隔离；
- 换版视为规则变更：同样本回放 + 首周 100% 人工抽查。

## 八、非功能设计

| 维度 | 要求 | 实现 |
|---|---|---|
| 性能 | 单渠道 80 万笔/日，批量窗口 ≤ 2h；查询 P95 ≤ 2s | 按日 + 渠道分区；匹配走批量内存计算 |
| 可用性 | 对账窗口 99.9%；断点续跑 | 批次状态机 + 幂等键，失败可单步重试 |
| 安全 | 字段级脱敏（卡号/户名/证件号）；最小权限 | RBAC + 数据域；导出二次确认 |
| 合规 | 账单与凭证留存 3 年，监管材料 5 年可配 | 冷热分层存储；删除需双人复核 |
| 可观测 | 批次成功率、匹配率、差异量、SLA 达成率 | 四个核心指标 + 异常告警 |
| 可运维 | 新渠道配置化接入；回滚 30 分钟内 | 映射表驱动；镜像版本化 + 灰度 |

## 九、部署架构

- **形态**：私有化内网部署，模型本地化（账单含个人金融信息，禁止出境/出网）。
- **组件**：应用服务（无状态，可水平扩展）｜ PostgreSQL（分区表 + 物化视图）｜ 对象存储（原始账单与证据）｜ 调度（XXL-Job/Quartz）｜ 模型服务（内网推理）。
- **数据流**：渠道文件 → 对象存储（留存原件）→ 解析入 PG → 匹配 → 差异/工单 → 结算文件输出。
- **备份**：数据库每日全量 + WAL 归档；对象存储版本化；恢复演练每季度一次。

## 十、关键取舍

| 取舍 | 选择 | 理由 |
|---|---|---|
| 自建 vs 采购 | 自建 | 口径与流程强定制，采购件改不动 |
| 单体 vs 微服务 | 单体优先，按模块分包 | 团队小、链路强一致，拆服务只会增加运维成本 |
| 实时 vs 批量 | T+1 全量 + 小时级增量 | 渠道账单本身是 T+1，实时化收益有限 |
| 规则 vs 模型 | 规则做确定性判断，模型做长尾排序 | 规则可解释、可回归；模型只补规则覆盖不到的部分 |
| BPMN vs 自研状态机 | 自研轻量状态机 | 流程只有 5 个状态，引入 BPMN 得不偿失 |

## 附：与仓库实现的关系

- `src/`：最小可运行版，实现了「核验 → 建单 → 提交 → 复核」闭环与只读问答，用于验证上述关键约束；
- `支付对账与差错追踪系统_交付/`：完整交付版，含 Web 服务、桌面客户端与 Agent 演示；
- 本文档描述的是生产形态（含渠道适配、分区、对象存储），两者在数据模型与状态机上保持一致。
