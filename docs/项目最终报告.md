## 一、项目概况

**问题**：支付运营每天要拿渠道账单和内部流水逐笔对账。跨日退款、手续费合并入账、主键与时区口径不一致，
会造成大量匹配失败；差异靠人工定位、建单、复核，链路长、易漏、留不下痕迹。现状是每天 180 笔未解释差异、
从发现到定位平均 6 小时、对账员每天 5 小时查异常。

**目标**：把对不上的账变成「可解释、可追溯、有人负责」的差异单。系统只做匹配、分类与线索，
**不改资金、不生成凭证、不替人下结论**。

**范围**：单渠道（一期），日 80 万笔。做对账、差异池、工单、双人复核、只读 AI 辅助；
不做资金划拨、会计凭证、自动调账、对外赔付。

## 三、系统实现

| 模块 | 文件 | 职责 |
|---|---|---|
| 路由与页面 | `app/main.py` | REST + SSE、异常处理、静态资源 |
| 差错处理 | `app/agent.py` | 核验（窗口/金额）、HMAC 凭证、建单、提交、复核 |
| Agent 循环 | `app/agent_loop.py` | 工具注册、计划、确认门、会话状态持久化 |
| 检索 | `app/retrieval.py` | 中文二元组分词 + BM25，零第三方依赖 |
| 模型 | `app/llm.py` | mock 摘录 / OpenAI 兼容流式 |
| 存储 | `app/db.py` | 8 张表（policy / batch / diff_record / verify_record / ticket / event / agent_run） |
| 前端 | `app/static/` | 三个页签（问答 / 差错 / Agent），原生 JS，无构建 |

代码量：`src/` 2,570 行（18 文件），`analysis/` 1,186 行（8 文件），交付版 9,734 行（30 文件）。

**三条防线**（都有测试）：

1. 写接口不收金额——金额一律从数据库重查；
2. 建单必须持有效凭证——HMAC 签名 + 库内记录 + 差异状态 + `diff_id` 唯一约束；
3. 四眼原则——复核人 ≠ 建单人，服务端强制，不靠前端隐藏按钮。

## 七、后续建议

1. **验收前置**：先书面定义「匹配正确」的四要素（主键、金额容差、时间窗、状态），否则匹配率指标不可比；
2. **补齐手工用例**：把 4 条未执行的故障/交付版用例放进演练环境跑一遍，验收报告才完整；
3. **AI 能力分级落地**：一期只做 L1/L2（只读），L3 动作建议需二期评估且必须双人复核；
4. **口径字典指定维护人**：否则匹配率会被口径漂移悄悄拉低；
5. **部署**：需要对外演示时，按 `部署手册` 用 Docker 部署，注意 SSE 必须关代理缓冲。
