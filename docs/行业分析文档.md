# 支付对账与差错追踪：行业分析

> 范围：行业体量与监管环境、对账为什么做不平、差错分类的业务口径、标准流程、技术与产品趋势、
> 开源实现参考。结论用于本项目「做哪些 AI 改造、做到什么边界」的判断。

## 一、对账在支付链路中的位置

一笔在线支付在系统内会产生四段记录，口径各不相同：

| 环节 | 记录内容 | 口径 |
|---|---|---|
| 订单系统 | 订单应收金额 | 业务口径 |
| 支付系统 | 支付成功金额（内部交易流水） | 内部口径 |
| 支付渠道（微信 / 支付宝 / 银联 / 网联） | 通过通道的金额 | 渠道口径，按结算日 |
| 银行 / 资金账户 | 实际到账金额 | 资金口径 |

四个概念要分清：**支付**是资金转移；**清分**是按机构/类型分类汇总、算出应结金额（只处理数据流）；**结算**是按清分结果净额轧差、完成资金划拨；**对账**是核对订单、支付流水、渠道流水三类主数据的 ID 关系、状态与金额是否一致；**差错追踪**是对不一致的记录建池、定位、派单、处理、销账。

本项目的落点在最后两环：对账 + 差错追踪，不碰清分的资金划拨，也不生成会计凭证。

## 二、体量与监管：为什么它是刚需

- 中国人民银行《2025 年支付体系运行总体情况》：全国支付系统处理业务约 **12807.07 万亿元**。
- **网联清算平台**：2025 年处理 **11949.24 亿笔 / 598.23 万亿元**，日均 32.74 亿笔、1.64 万亿元。
- **银联跨行支付系统**：2025 年处理 **3803.80 亿笔 / 279.41 万亿元**，日均 10.42 亿笔、7655.17 亿元。

体量决定了对账是高频、海量、强合规的后台刚需：任何异步漏数、网络超时、重复回调都会累积成资金差异，只能靠系统化对账兜底。

监管层面的三条硬约束：

1. **断直连**：跨行清算必须走网联或银联，不能绕开直连银行；
2. **备付金 100% 集中交存**：备付金与自有资金严格隔离，监管要求完善全流程内控与对账机制；
3. **留痕可审计**：对账与差错处理记录本身就是合规审计证据，要求可追溯、可复盘、可导出。

> 对本项目的直接影响：**差异处理必须留痕、复核必须可证明、原始账单必须可回溯**——这三条写进了需求边界，属于不可退让项。

## 三、为什么会「对不上账」

| 成因 | 说明 | 对应差错类型 |
|---|---|---|
| 掉单/漏单 | 支付成功但内部未收到回调，状态未更新；或轮询超时未询到 | 长款 / 状态不符 |
| 重复扣款/重复退款 | 超时后重试，同一笔被执行两次（幂等缺失） | 重复单 |
| 金额不符 | 流水能对上但金额不一致，常见于手续费扣减、找零未退、优惠分摊口径不同 | 金额不符 |
| 状态不符 | 流水与金额一致，订单状态停在「未支付/支付中」 | 状态不符 |
| 双边金额不一致 | 明细可配平，结算净额对不上（费率、贴息、清算扣费） | 手续费/汇率差异 |
| 汇率差异 | 跨境多币种，汇率取值口径不同 | 手续费/汇率差异 |
| 在途时间差 | T+1 结算时交易尚未入账，属正常时间差而非差错 | 跨日退款 / 在途 |

后三类最容易「误判」：它们不是数据错误，而是**口径与时序**问题。把口径差异当差错建单，会白白增加处理量；把真差错当在途放过，会错过追偿窗口。这也是本项目把「口径字典」和「7 天回溯窗口」列为一等公民的原因。

## 四、差错分类的业务口径

| 结果 | 含义 | 典型成因 | 处理方向 |
|---|---|---|---|
| 对平 | 笔数、金额、状态一致 | —— | 生成结算流水 / 付款文件 |
| 长款 | 平台多收（渠道有记录、平台无有效订单） | 系统掉单、BUG、轮询未询到 | 补单或退款，定时轮询兜底 |
| 短款 | 平台少收（平台显示成功、渠道未收到） | 请求未送达渠道 | 调单核查、补偿扣款 / 冻结订单 |
| 双边金额不一致 | 明细对上、净额对不上 | 系统 BUG、轮询遗漏 | 修正金额并加轮询 |
| 金额/状态不一致 | 金额对、状态未更正 | 状态轮询失败、找零未退 | 退找零、补状态轮询 |
| 汇率/手续费差异 | 币种或费率口径差 | 汇率取值、费率规则 | 修正汇率 / 重算费用 |

系统内部把上表细化为**七类**用于初判：长款、短款、金额不符、状态不符、重复单、跨日退款、手续费/汇率差异。

## 五、标准对账与差错追踪流程

1. **日切拉单**：日切后按渠道 + 结算币种拉取交易账单与结算账单；
2. **解析入库**：判断渠道与账单类型 → 解析 → 转统一结构入库 → 建对账批次（防重复对账）；
3. **匹配核对**：明细逐笔比对（订单号/流水号、金额、时间、手续费）+ 汇总核对（总笔数、总金额、总手续费）；
4. **结果分类**：对平 / 各类差异，差异汇入差错池；有差错的渠道暂不生成结算流水，处理后再结算；
5. **差错追踪销账**：建单 → 上传凭证 → 定位原因 → 补单/退款/调单/补偿扣款 → 记录处理人与时间；
6. **时间差回溯**：预留回溯窗口（通常 7 天），窗口内因在途未匹配的交易后续对平后自动清除差异；
7. **平账归档**：生成结算流水或付款文件，结果可导出，全程留痕。

## 六、技术与产品趋势

- **从 T+1 批量人工，走向准实时**：关键交易实时校验 + 日终批量复核；
- **规则引擎 + AI 异常检测**：规则处理确定性差异，模型处理长尾（重复模式、金额离群、未知收款方、缺摘要）；
- **业财一体化**：订单流、资金流、发票流打通，对账直接服务财务核算；
- **可审计**：差异原因、处理人、凭证、时间戳全程留痕，满足备付金与反洗钱审计；
- **SaaS 化与开放 API**：第三方对账服务向中小商户输出，降低自建门槛。

> 趋势判断：AI 在行业里的位置是**降低人工复核量**（排序、推荐原因），不是替代人做定性。本项目据此把 AI 限定在 L1（线索排序）/ L2（原因推荐），L3（动作建议）放到二期评估，L4（自动执行）明确禁止。

## 七、开源实现参考

| 项目 | 技术栈 | 可参考点 |
|---|---|---|
| DaxPay（dromara/dax-pay） | Java、Spring Boot、PostgreSQL、Redis | 完整交易闭环、通道对接分离、签名验签；历史版本有对账单下载与差异单查看 |
| Jeepay（jeequan/jeepay） | Java、Spring Boot、MySQL、Redis、Vue | 交易/退款/转账/分账完整实现，适合看订单、流水、退款如何建模 |
| Hyperswitch（juspay） | Rust 核心 + 全栈 | 内置 Reconciliation Engine：支付数据 × PSP × 银行三方匹配，标记未匹配记录并分类 |
| hyperswitch-reconciliation | Rust | 独立对账框架，小而专，适合拆解对账引擎设计 |
| formancehq/reconciliation | Go | 内部账本与支付商数据对账，开放财务栈组件 |
| OpenRecon | Python 3.9+ | 零依赖对账 CLI，decimal 精确、确定性、CI 友好，适合看最小对账算法 |

**共性结论**：成熟实现都把「原始账单」与「标准化事件」分层存，匹配结果与差异单分开，差异单挂证据链；AI 只出现在排序和推荐层。这与本项目的架构选择一致。

## 八、对本项目的启示（结论）

1. **口径先于算法**：三个编号、四条时间轴不统一，再好的匹配也会制造假差异；
2. **差异必须可解释**：每条差异至少一条证据 + 一个分类，否则只是把人工困惑搬进系统；
3. **追偿有窗口**：7 天是业务约束不是技术限制，系统必须前置提醒而不是事后统计；
4. **AI 只做辅助**：L1/L2 降低复核量，定性与资金动作必须人签；
5. **审计即产品**：留痕不是附加功能，而是能被内审与监管接受的前提。
